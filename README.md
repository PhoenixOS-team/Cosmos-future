Hello! I am Felek, an operating system developer on the CosmosOS framework and a person who understands computers and how they work at a low level. In this article, I would like to discuss how I see the future of the Cosmos framework.

Before diving into the main topic, I would like to recall what operating systems on CosmosOS are now. The answer is very complex, and there is probably no single correct answer, because every OS on Cosmos is unique and interesting. You can, of course, single out a number of the most well-known and advanced operating systems, such as AuraOS, CrystalOS, PhoenixOS, etc. It is important here to understand what each of them represents. I do not want to go deeper into the topic of which of them is better and is the “ideal” operating system on Cosmos; I would simply like to highlight one curious thing: these operating systems do not have backward compatibility. In effect, this means that programs for one OS are completely incompatible with programs for others. Here one must not forget the fact that many programs for such OSes as AuroraOS, CrystalOS, etc. are written in C# and cannot be modified from within the operating system, which I want to call the main problem of Cosmos: because of the ease of creating programs in C#, developers completely forget about the existence of the main Unix rule: one program should do its job. Through the prism of Cosmos, this means that the operating system should only provide an API for developing, launching, and operating applications for it, rather than imposing its “application ideology” on the end user. Some operating systems, such as AuroraOS, tried to solve this problem by implementing Lua interpreters, which allowed more ambitious ideas to be realized. Despite this, Cosmos has essentially been in a state of “maturing” for the last 6–8 years. It evolved from simple operating systems to advanced monolithic kernels that had a good graphical interface (comparable to Windows 7/XFCE). But, as was said in an issue on GitHub for Cosmos gen2, Cosmos gen2 had a number of problems that slowed down the development of operating systems. And now, at a time when CosmosOS has received the Cosmos gen3 update, we can understand how big a leap it made in such a short time. For example, StarELF appeared, and later its add-on, AESC. It would also be a crime not to mention PhoenixOS, an OS that did a lot, including: a C compiler and a prototype package manager. It was PhoenixOS that proposed and actually implemented the “main Unix rule.” At the same time, AuraOS releases its own package manager and browser, which, in my opinion, opens up limitless possibilities ahead. However, despite this, many operating systems on CosmosOS continue to follow gen2 technologies. That is precisely why I would like to propose a project for the separation of responsibilities of operating systems based on CosmosOS.

The idea is to make it a de facto standard for operating systems to try as much as possible to implement their components as application programs (commands, graphical windows, etc.). That is why it would be worth choosing one of the programming languages supported by CosmosOS (at the moment these are: Lua, Teal, and other Lua implementations); there is also the P language, which is being actively developed by me, and in the future I would like to make it one of the key languages for Cosmos. Therefore, I would like to suggest what a programming language for Cosmos should have:
- Standard API (Math, IO, OS, etc.)
- API for working with Cosmos
- API for working with graphics in Cosmos

I would like to highlight what each part should be responsible for. This is perhaps the most sensitive and difficult part. In essence, what every distribution based on Cosmos should do is provide a minimal set of functionality so that other applications can be launched. AESC or Lua/P would be ideal for this. The next thing is the initialization and launch of the console/graphical environment. I believe that customization should be configured in a config, and there should be a certain “unified” initialization system that will: 1. Check the PC components. 2. Launch the graphical environment/terminal. The terminal (console) should be a separate program that will manage work with commands. All commands should also be separate programs (whether ls, mount, umount, fastfetch, or something else). In essence, the main idea here is that the final distribution based on CosmosOS should be only PID-1 and be responsible for the correct operation of basic programs.

Of course, this is a fairly large list, and I doubt that many operating systems will switch to it; however, if this happens, Cosmos could be considered an operating system for servers and desktop. Although this is essentially a utopia, I think that all developers of Cosmos and operating systems based on it want this.
